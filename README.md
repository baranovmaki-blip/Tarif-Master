# Тариф-Мастер — гибридный Telegram-бот с CRM

Один файл `bot.py`. Никаких вопросов клиенту — `/start` сразу одним экраном
показывает продукт, тарифы (маркетингово оформленные), как происходит
подключение и кнопки «Оплатить» / «Связаться с менеджером» / «Отказаться».
При этом каждый диалог автоматически заводит заказ в простой CRM с
уникальным номером (#1001, #1002...), а на решающих этапах бот подключает
вас (или менеджера) вручную — это и есть «гибридная» часть:

- Кнопка **«💬 Связаться с менеджером»** доступна на этапе предложения тарифа
  и во всех сообщениях после него — клиент может позвать человека в любой момент,
  и сразу получает прямую ссылку на чат с менеджером (`MANAGER_TELEGRAM_USERNAME`).
- Если клиент пишет что-то похожее на возражение («дорого», «подумаю», «не
  уверен», «дешевле», «сравните») — бот сам предлагает позвать менеджера,
  не дожидаясь явной просьбы.
- Если клиент ничего не решает — бот сам напоминает о себе через 3 минуты,
  потом ещё раз с растущим интервалом (+5, +10, +15...), пока не ответит.
- После оплаты бот **сразу сам** заходит на **mycompany.beeline.ru**, вводит
  вашу бизнес-почту, получает одноразовую ссылку письмом и пересылает её
  клиенту — без вашего участия. Вы получаете уведомление о каждом шаге, но
  ничего нажимать не нужно.
- Если автоматика не смогла (сайт Билайна изменился, письмо не пришло за
  90 сек) — бот не молчит и не помечает заказ подключённым раньше времени:
  статус остаётся `paid`, а вам приходит уведомление с кнопками
  «✅ Подключить вручную» / «❌ Отказать» — это запасной путь на случай сбоя
  автоматики, не основной сценарий.

Все заказы хранятся в словаре `orders` и сохраняются в `orders.json` — не
теряются при перезапуске бота (см. предупреждение про деплой на Render ниже).
Каждое изменение статуса заказа дополнительно дублируется в Google Sheets
(через Apps Script, см. раздел про Sheets ниже), а по команде `/report`
(и автоматически каждое воскресенье в 20:00) бот присылает сводный отчёт.

**Проверено вживую** (реальным ботом, реальным Telegram API, реальными
запросами к серверу ЮKassa и реальными HTTP-запросами) прямо при разработке,
несколькими прогонами:
- Полный сценарий от `/start` до оплаты, менеджера, возражений и `/stats` —
  без единой ошибки.
- Запрос на создание платежа реально уходит на `api.yookassa.ru` — с
  настоящими `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY` отработает так же,
  просто вернёт успех вместо ошибки авторизации (это единственное, что не
  проверялось живьём — не было под рукой реальных ключей ЮKassa; то же самое
  верно и для Google Sheets — не было реального опубликованного Apps Script).
- CRM: `/start` → заказ #1001 → «Оплатить» → (смоделированное подтверждение
  оплаты) → статус `paid`, уведомление с кнопками → `/connect` → статус
  `connected`, клиент получил инструкцию; второй заказ → сразу отказ →
  статус `declined`. Оба заказа с верными номерами и статусами корректно
  сохранились в `orders.json`.
- Google Sheets: с ненастроенным `GOOGLE_SHEETS_URL` синхронизация тихо
  пропускается; на реальный рабочий адрес (проверено на стороннем HTTP-эхо
  сервисе) запрос уходит и успешно завершается; на недоступный адрес —
  ошибка аккуратно ловится, вам приходит уведомление в Telegram, бот не
  падает и ничего не теряет (заказ уже сохранён в `orders.json`).
- `/report` без аргументов, `/report ГГГГ-ММ-ДД ГГГГ-ММ-ДД`, некорректный
  формат дат и еженедельный автоотчёт — всё проверено, ошибок нет.
- **Автоматизация mycompany.beeline.ru — проверена полностью, реальным
  сквозным прогоном.** Сначала протестировал по частям (селекторы на живой
  странице, отправка формы тестовой несуществующей почтой — сайт ответил
  "Компаний... не найдено", разбор HTML-письма на синтетических данных), а
  затем — с вашими настоящими `EMAIL_ACCOUNT`/`EMAIL_APP_PASSWORD`: реальная
  заявка на Билайн → реальное письмо → ссылка найдена за ~3 секунды →
  доставлена в Telegram → статус заказа сменился на `connected`. По пути
  нашёл и исправил ещё несколько реальных проблем (IMAP не понимал кириллицу
  в поиске по теме, скорость проверки почты — 59 сек на реальном ящике на
  2850 писем вместо секунд, отсутствие таймаута у `imaplib` один раз привело
  к зависанию навсегда). Финальное решение ищет письмо по адресу отправителя
  (`BEELINE_SENDER_EMAIL`, подтверждён по реальному письму), а не по
  угаданному тексту темы — это и надёжнее, и быстрее.

## ⚠️ О рисках автоматизации mycompany.beeline.ru

- **Хрупкость.** Это не официальный API, а автоматизация обычной веб-страницы.
  Если Билайн изменит вёрстку страницы — селекторы могут перестать находить
  поле/кнопку, и подключение автоматически перестанет работать (бот это
  заметит и напишет вам, но чинить придётся вручную — см. "Как это устроено
  внутри").
- **EMAIL_APP_PASSWORD — чувствительные данные.** Это ключ от вашей реальной
  почты (пусть и ограниченный "паролем приложения", а не основным паролем).
  Если он утечёт вместе с кодом — доступ к почте получит кто угодно. Не
  публикуйте `bot.py` с вписанным реальным паролем в открытый репозиторий.
- Если позже появится официальный B2B API от Билайна для партнёров — стоит
  перейти на него: он не сломается от редизайна сайта и не завязан на чтение
  вашей личной почты.

## 1. Установка зависимостей

```bash
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
python3 -m playwright install chromium
```

Последняя команда (`playwright install chromium`) обязательна отдельно от
`pip install` — Playwright скачивает сам браузер (headless Chromium)
отдельным шагом, это нормально, займёт минуту-две.

## 2. Получение ключей

- **BOT_TOKEN** — напишите [@BotFather](https://t.me/BotFather) в Telegram,
  `/newbot` (или используйте существующего бота), скопируйте выданный токен.
- **CLAUDE_API_KEY** — в [console.anthropic.com](https://console.anthropic.com)
  → API Keys → Create Key.
- **ADMIN_CHAT_ID** — ваш личный Telegram id или id группы для уведомлений и CRM-команд.
  Проще всего узнать через [@userinfobot](https://t.me/userinfobot) — он в
  ответ пришлёт ваш id.
- **MANAGER_CHAT_ID** (необязательно) — если хотите, чтобы уведомления и
  CRM-команды были доступны ещё и второму человеку (менеджеру) — узнайте его
  id так же через [@userinfobot](https://t.me/userinfobot). Можно оставить
  заглушку, если менеджер — это вы же, через `ADMIN_CHAT_ID`.
- **MANAGER_TELEGRAM_USERNAME** — username менеджера (без @) для прямой
  ссылки, которую получает клиент при нажатии «Связаться с менеджером».
- **YOOKASSA_SHOP_ID** и **YOOKASSA_SECRET_KEY** — в личном кабинете ЮKassa
  ([yookassa.ru](https://yookassa.ru), после регистрации магазина) →
  Настройки → раздел «Магазин» (shopId) и «API-ключи» (секретный ключ). Для
  тестов можно включить тестовый режим магазина — ключи будут тестовыми,
  платежи не спишут реальные деньги.
- **GOOGLE_SHEETS_URL** — ссылка на веб-приложение Google Apps Script (как
  получить — см. раздел «Настройка Google Sheets» ниже, код скрипта — в
  `google_apps_script.gs` рядом с этим файлом).
- **TIMEZONE_OFFSET_HOURS** (необязательно, по умолчанию `3` — МСК) — часовой
  пояс, по которому бот определяет "воскресенье, 20:00" для еженедельного отчёта.
- **EMAIL_ACCOUNT** — ваша **бизнес-почта, уже зарегистрированная** на
  [mycompany.beeline.ru](https://mycompany.beeline.ru/auth) (Мой Билайн для
  бизнеса) — именно её бот будет вводить на этой странице и именно в её
  входящих будет искать письмо со ссылкой.
- **EMAIL_APP_PASSWORD** — **не обычный пароль** от почты, а специальный
  "пароль приложения" Gmail. Как получить: [myaccount.google.com/apppasswords](https://myaccount.google.com/apppasswords)
  (нужна двухфакторная аутентификация, включённая на аккаунте) → создать
  пароль приложения → скопировать 16-значный код без пробелов.
- **BEELINE_SENDER_EMAIL** (необязательно, уже настроено на реальный адрес —
  `b2bmycompany@beeline.ru`) — бот ищет письмо по адресу отправителя, а не по
  теме. Менять не нужно, если Билайн не сменит адрес рассылки.

## 3. Куда вставить ключи

Два варианта — любой:

**А. Прямо в код** — откройте `bot.py`, в начале файла замените, например:
```python
BOT_TOKEN = os.environ.get("BOT_TOKEN", "YOUR_BOT_TOKEN")
```
на
```python
BOT_TOKEN = os.environ.get("BOT_TOKEN", "12345:AAвашТокен")
```
и аналогично для остальных переменных из раздела 2.

**Б. Переменные окружения** (безопаснее — ключи не остаются в коде):
```bash
export BOT_TOKEN="12345:AAвашТокен"
export CLAUDE_API_KEY="sk-ant-..."
export ADMIN_CHAT_ID="123456789"
export MANAGER_CHAT_ID="987654321"              # необязательно
export MANAGER_TELEGRAM_USERNAME="MinBar_Co"
export YOOKASSA_SHOP_ID="123456"
export YOOKASSA_SECRET_KEY="live_..."
export GOOGLE_SHEETS_URL="https://script.google.com/macros/s/.../exec"
export EMAIL_ACCOUNT="business@gmail.com"
export EMAIL_APP_PASSWORD="abcdabcdabcdabcd"       # 16 символов без пробелов
export BEELINE_SENDER_EMAIL="b2bmycompany@beeline.ru"  # необязательно, уже верно по умолчанию
```

## 4. Запуск локально

```bash
python bot.py
```

Бот сразу начнёт работать (long polling — сам опрашивает Telegram, никакой
публичный адрес не нужен). Напишите ему `/start` в Telegram и проверьте
сценарий, включая нажатие «Оплатить».

## Настройка Google Sheets

1. Создайте новую Google-таблицу: [sheets.google.com](https://sheets.google.com) → Создать.
2. В ней: меню **Расширения** → **Apps Script**.
3. Откроется редактор кода — выделите всё в файле `Code.gs` (Cmd/Ctrl+A) и
   удалите, вставьте вместо этого весь код из `google_apps_script.gs`
   (лежит рядом с `bot.py`).
4. Сохраните проект (значок дискеты).
5. **Развернуть** (кнопка справа сверху) → **Новое развёртывание** →
   значок шестерёнки ⚙️ рядом с "Выбор типа" → **Веб-приложение**.
   - Execute as: **Я** (Me).
   - Who has access: **Все** (Anyone) — иначе бот не сможет писать в таблицу
     без авторизации Google.
6. Нажмите **Развернуть**. Google попросит подтвердить разрешения — это
   нормально для собственного скрипта (Advanced → Go to project (unsafe) → Allow).
7. Скопируйте выданную ссылку (заканчивается на `/exec`) и вставьте её в
   `GOOGLE_SHEETS_URL` в `bot.py` (или в переменную окружения).
8. Готово — при следующем изменении статуса любого заказа в таблице
   появится/обновится строка на листе «Заказы», а лист «Отчёты»
   пересчитается автоматически.

⚠️ Если позже будете редактировать код в `google_apps_script.gs` — не
забудьте создать **новую версию** развёртывания (Deploy → Manage deployments
→ карандаш ✏️ → New version → Deploy), иначе правки не попадут в уже
опубликованную ссылку.

## 5. Деплой на сервер (чтобы работал 24/7)

### Render (рекомендую)
1. Залейте папку в git-репозиторий.
2. Render → **New +** → **Background Worker** (не Web Service — боту не
   нужен входящий HTTP, он сам опрашивает и Telegram, и ЮKassa).
3. Build command: `pip install -r requirements.txt`. Start command: `python bot.py`.
4. В Environment добавьте все ключи из раздела 2.
5. Deploy — бот запустится и будет работать постоянно, включая фоновую
   проверку платежей раз в 30 секунд.

⚠️ **Важно про `orders.json` на Render**: бесплатный диск на Render —
эфемерный. Локальные перезапуски процесса (крах, ручной рестарт) файл
переживёт, но **новый деплой** (пуш кода) создаёт контейнер заново и стирает
`orders.json` — вся история заказов потеряется. Если это критично, либо
переходите на платный тариф с постоянным диском (Render → Disks), либо
попросите перенести хранение заказов в настоящую БД (Postgres и т.п.) —
структура кода это допускает без больших переделок (`orders`/`_save_orders`/
`_load_orders` — единственные места, которые нужно поменять).

### PythonAnywhere
Подойдёт только платный тариф ("Hacker" и выше) — на бесплатном там
заблокированы исходящие запросы к произвольным сайтам (в том числе к
`api.telegram.org`, `api.anthropic.com` и `api.yookassa.ru`), бот не сможет
ни получать сообщения, ни звать Claude, ни проверять платежи. На платном:
загрузите файлы, заведите **Always-on task** с командой `python3 bot.py`.

## Про требования из ТЗ, которые я осознанно заменил

- `requests` → для Claude использую официальный пакет `anthropic`
  (рекомендованный Anthropic способ — сам разбирает ошибки и ретраит сбои).
  Для ЮKassa использую `aiohttp` вместо `requests`, потому что весь бот и так
  работает на asyncio (`python-telegram-bot`), а `requests` — синхронная
  библиотека, которая заблокировала бы весь бот на время запроса к ЮKassa;
  `aiohttp` этого не делает.
- `flask` → не нужен: боту не нужно принимать входящие HTTP-запросы. Новые
  сообщения бот получает через long polling у Telegram, а статус платежей —
  через периодическую (раз в 30 сек) активную проверку у ЮKassa, а не через
  вебхук от неё.
- `threading.Timer` / отдельный APScheduler → использую встроенный в
  `python-telegram-bot` `JobQueue` (пакет `python-telegram-bot[job-queue]`,
  под капотом тот же APScheduler) — он рассчитан на то, чтобы безопасно
  работать в одном asyncio-цикле с самим ботом, без ручной синхронизации
  между потоками.

## CRM-команды (только из ADMIN_CHAT_ID / MANAGER_CHAT_ID)

| Команда | Что делает |
|---|---|
| `/orders` | Список всех заказов: номер, имя, статус, дата создания. |
| `/order 1001` | Подробности по одному заказу: имя, телефон, оператор, тариф, статус, все даты. |
| `/new` | Только заказы со статусом `new` (ещё не оплачены). |
| `/paid` | Оплаченные заказы (`paid`) — обычно это только те, где автоматика не смогла подключить сама и нужна ручная попытка. |
| `/connect 1001` | Запасной вариант на случай, если автоматика после оплаты не сработала: повторяет попытку получить ссылку у Билайна и переслать клиенту. То же самое делает кнопка «✅ Подключить вручную». |
| `/decline 1001` | Меняет статус на `declined` и присылает клиенту вежливый отказ. То же самое делает кнопка «❌ Отказать». |
| `/stats` | Сколько всего заказов и в каких статусах — за всё время (не только за сегодня). |
| `/report` | Сводный отчёт за сегодня: заказы по статусам, выручка, конверсия, средний чек. |
| `/report 2025-09-01 2025-09-30` | Тот же отчёт, но за произвольный период. |

Тот же отчёт, что и `/report`, бот присылает **автоматически каждое
воскресенье в 20:00** (часовой пояс — `TIMEZONE_OFFSET_HOURS`) за прошедшую
неделю, без вашего запроса — это `weekly_report_job` в коде.

Статусы жизненного цикла заказа: `new` → `paid` → `connected`, либо в отказ
(`declined`) на любом из первых двух этапов. При каждом изменении статуса
все админы получают уведомление вида:

```
🔄 Статус заказа #1001 изменён:
   new → paid

👤 Клиент: Анна
📞 Телефон: не указан
📌 Тариф: уточняется у клиента
💰 Сумма: 1500 ₽
```

**Про поля «Телефон» и «Тариф»**: бот сознательно не задаёт клиенту вопросов
(по вашей же более ранней просьбе убрать все "сколько платите"/"что
предпочитаете") — поэтому телефон в CRM всегда «не указан», а тариф —
«уточняется у клиента», пока вы не узнаете это сами в переписке (например,
после нажатия клиентом «Связаться с менеджером») и не спросите его руками.
Если хотите, чтобы бот сам спрашивал телефон/тариф и заполнял эти поля
автоматически — это отдельная переделка диалога, скажите отдельно.

## Как это устроено внутри (если захотите поправить)

- `orders` — словарь `номер заказа -> данные`, в памяти, сохраняется в
  `orders.json` при каждом изменении (`_save_orders()`), загружается при
  старте (`_load_orders()`, вызывается в `main()`).
- `_generate_order_number()` — простой счётчик (`_next_order_number`),
  начинается с 1001, сохраняется вместе с заказами (чтобы не начать
  нумерацию заново после перезапуска).
- `_set_order_status()` — меняет статус локально (в `orders` + `orders.json`).
- `send_to_google_sheets()` — отправляет текущее состояние заказа в Apps
  Script (POST JSON). Молча ничего не делает, если `GOOGLE_SHEETS_URL` не
  настроен; при ошибке — уведомляет админов в Telegram, но данные не теряет
  (они уже в `orders.json`).
- `_update_order_status()` — единая точка для смены статуса: вызывает и
  `_set_order_status()`, и `send_to_google_sheets()`. Все места в коде,
  которые меняют статус заказа, используют именно её.
- `_build_report()` / `/report` / `weekly_report_job` — сводная статистика
  (заказы по статусам, выручка, конверсия, средний чек) за произвольный
  период; еженедельный отчёт — тот же расчёт за последние 7 дней, вызывается
  по расписанию (`run_daily`, воскресенье 20:00).
- `request_beeline_link()` — Playwright, headless Chromium: заходит на
  `BEELINE_AUTH_URL`, вводит `EMAIL_ACCOUNT` в поле `input[name="email"]`,
  жмёт `button[type="submit"]`.
- `_check_inbox_once()` / `get_confirmation_link()` — IMAP-проверка почты
  (блокирующий вызов `imaplib` уводится в отдельный поток через
  `asyncio.to_thread`, чтобы не подвешивать остальной бот), опрашивается раз
  в `CONFIRMATION_EMAIL_POLL_INTERVAL_SECONDS` секунд, пока не найдёт
  сегодняшнее письмо от `BEELINE_SENDER_EMAIL` или не истечёт
  `CONFIRMATION_EMAIL_TIMEOUT_SECONDS`. Ищем по адресу отправителя (не по
  теме — она на кириллице, а IMAP SEARCH с не-ASCII текстом не работает без
  ручной возни с "literal"-форматом) и не только среди непрочитанных — иначе
  письмо, уже открытое в самом Gmail, окажется невидимым для бота (поймал
  это вживую). У самого IMAP-соединения выставлен `timeout=20` — без него
  `imaplib` может зависнуть навсегда, если сервер промолчит вместо ответа
  (тоже поймал вживую, после нескольких быстрых подключений подряд).
- `auto_register_tariff()` — склеивает эти два шага, сама уведомляет админов,
  если что-то пошло не так на любом из этапов, и возвращает либо ссылку,
  либо `None`.
- `_connect_order()` — вызывается и кнопкой «Подключить», и `/connect`;
  запускает `auto_register_tariff()`, и только при успехе меняет статус на
  `connected` и пересылает ссылку клиенту — при неудаче статус остаётся
  `paid`, чтобы заказ не потерялся и был виден в `/paid`.
- `check_pending_payments_job` — фоновая задача, каждые 30 секунд (константа
  `PAYMENT_CHECK_INTERVAL_SECONDS`) проверяет статус всех заказов со статусом
  `new` и привязанным `payment_id` через ЮKassa. При `succeeded` —
  переводит заказ в `paid` и уведомляет вас с кнопками, а не подключает
  тариф сама.
- `remind_payment_job` — разовая задача, планируется в момент создания
  платежа на +30 минут (константа `PAYMENT_REMINDER_DELAY_SECONDS`). Если к
  этому моменту заказ всё ещё `new` — шлёт напоминание.
- `idle_nudge_job` — разовая задача на +3 минуты после показа предложения
  тарифа (`IDLE_NUDGE_DELAY_SECONDS`), сама себя перепланирует с растущим
  интервалом (`IDLE_NUDGE_STEP_SECONDS`) — пока клиент не нажмёт любую
  кнопку («Оплатить», «Отказаться» или «Связаться с менеджером»).
- `_looks_like_objection()` — простая проверка по ключевым словам
  (`OBJECTION_KEYWORDS`), срабатывает раньше, чем сообщение уходит в Claude.
- `/check_payment` — то же самое, что делает фоновая проверка, но по запросу
  клиента прямо сейчас, для конкретно его заказов.

## Рекомендации по промпту — если хотите умнее распознавать возражения

Сейчас возражения ловятся по ключевым словам (`OBJECTION_KEYWORDS` в начале
`bot.py`) — это быстро и предсказуемо, но ловит только буквальные фразы.
Если захотите распознавать возражения умнее (перефразированные, без прямых
слов из списка) — можно попросить Claude классифицировать каждое сообщение
клиента отдельным вызовом:

```
Ты определяешь, содержит ли сообщение клиента возражение против покупки
(сомнение в цене, желание подумать, сравнить с другими вариантами, неуверенность).
Сообщение клиента: "{текст сообщения}"
Ответь только "да" или "нет".
```

Такой вызов можно добавить в `question_during_offer()` перед проверкой
`_looks_like_objection()` как более точный (но и более медленный/платный)
второй уровень проверки — вызывать его имеет смысл, только если ключевые
слова не сработали, чтобы не тратить лишние запросы к Claude на каждое
сообщение.

Промпт для персонализированных ответов на вопросы клиента — уже встроен в
`get_ai_answer()` в `bot.py`, при желании отредактируйте текст прямо там.
